Данный раздел не загружается из Галактики, а нагрузка формируется в самой системе.
Таблица со столбцами:

Снизу кнопка [Добавить]
При нажатии на ФИО попадаем в одинаковую форму добавления или редактирования, только при редактировании поля предзаполнены. При редактировании снизу кнопки «Сохранить» и «Удалить».
Поля:
1) ФИО: выбор из «своих» сотрудников, автокомплит по аналогии с распределением нагрузки в таблице.
Должность и доля ставки подтягиваются оттуда же. Если ГПХ, то должность «ГПХ».
2) Язык (селект — русский/английский)
3) Индивидуальные консультации (осень) - инпут число (может быть дробное)
4) Индивидуальные консультации (весна) - инпут число (может быть дробное)
5) КСРО (осень) - инпут число (может быть дробное)
6) КСРО (весна) - инпут число (может быть дробное)
Контроль:
    • Нельзя добавить одному ППС еще одну с тем-же языком. То-есть на одного человека может быть максимум 2 строки.
    • По индивидуальным консультациям в один семестр не может быть более 32 часов на ставку (пропорционально, если ставка, например, 0,5 то не более 16 часов). Суммируется по всем строкам этого ППС (если есть).
    • По КСРО. Если ставка 0,5 и более, то также как ИК — не более 32 часов на ставку пропорционально, а если ставка менее 0,5 то просто не более 16 часов в семестр (без учета пропорций).

Сделанный выбор надо экспортировать через отдельный скрипт в xml.
Пример:
<?xml version="1.0" encoding="UTF-8"?>
<Data_Root>
<Data>
<Collection name="Data.ContentOfLoad" caption="Содержание нагрузки расписания" child_tags="Object">

<Object LoadId="1" class_id="ContentOfLoad">
<Collection name="Prop_Values" child_tags="prop_value" caption="Свойства">
	<prop_value prop_name="Amount" value="777.00"></prop_value>
	<prop_value prop_name="TypeOfContingent" value="4"></prop_value>
	<prop_value prop_name="UID_KindOfWork" value="26003.281474976710751"></prop_value>
	<prop_value prop_name="UID_Discipline" value="26006.281474976727808"></prop_value>
	<prop_value prop_name="UID_Chair" value="25031.281474976756214"></prop_value>
	<prop_value prop_name="UID_Semester" value="1"></prop_value>
	<prop_value prop_name="UID_Language" value="25031.281474976715638"></prop_value>
	<prop_value prop_name="UID_FacultyPerformer" value="25031.281474976751459"></prop_value>
</Collection>
</Object>

</Collection>
</Data>
</Data_Root>

Повторяющаяся часть (строка) это Object
В LoadId надо выгружать какой-то уникальный идентификатор, по которому потом можно будет находить нагрузку (какой нибудь длинный типа random md5).

    • Amount — число часов
    • TypeOfContingent — всегда 4
    • UID_KindOfWork — брать UID из справочника KindOfWork.xml по именам «Индивидуальные консультации» или «Контроль самостоятельной работы обучающихся»
    • UID_Discipline - брать UID из справочника Discipline.xml по именам «Индивидуальные консультации» или «Контроль самостоятельной работы обучающихся»
    • UID_Chair — UID кафедры (Chair.xml)
    • UID_Semester — UID семестра (Semester.xml)
    • UID_Language — UID языка (Language.xml)
    • UID_FacultyPerformer — факультет кафедры (UID_Faculty в Chair.xml)

Нагрузка создается и в следующем импорте она должна появиться в ContentOfLoad.xml, при этом в ContentOfLoadStaff.xml ему соответствовать ничего не будет.
Нужно вновь созданную таким методом распределение выгружать отдельным скриптом (таким же как https://lkzk.unn.ru/once/export_selected_nagruzka.php). Как сопоставлять опишу позже.

Когда включен режим, когда завкаф не может редактировать этот раздел, то таблица показывается у него в режиме ридонли, но по данным, которые приходят из Галактики через  ContentOfLoad.xml, выбирать по UID_KindOfWork, соответствующим этим двум видам (индивидуальные консультации и КСРО).


Режимы работы ЛК ЗК

Во вкладке «Режимы работы» выбираются режимы:
    • Закрыто
    • Заполнение
    • Выверка
    • Архив

Закрыто
В Галактике пока формируются первичные данные по нагрузке.
Все данные находятся в режиме ридонли у УОУП, у завкафов вообще ничего не показывается, при входе пишет что «Подготовка данных для распределения нагрузки».
Данные по нагрузке каждый день импортируются в ЛК ЗК и показываются для просмотра УОУП.

Заполнение
Данные по нагрузке доступны для редактирования завкафу, работает привязка преподов, отправка запросов в УОУП и т. п. 
Каждый день данные по нагрузке загружаются из Галактики. При этом все привязки, сделанные там, игнорируются и не переходят в ЛК ЗК, будто у всех Lecturer стоит -1.
Суффиксы учитываются только для того чтобы учесть в одну базу несколько дисциплин, суффиксы получаемые из-за дробления на ППС игнорируются.
Распределения (сплиты), сделанные завкафами хранятся и накладываются для показа в таблицах на нагрузку из Галактики, все суммарные расчеты часов делаются только по сплитам. 
Разделы, где нагрузка создается руками (ИК/КСРО, аспирантура) данные показываются также только те, которые прописаны в ЛК ЗК, если есть нагрузка данных типов из Галактики, то она тоже игнорируется.
Работает формирование выгрузок (xml) с данными по сделанным распределением на Lecturer и данными по созданию новых нагрузок (КСРО и пр.).

Выверка
Важный переход из заполнения к выверке. При этом все данные, занесенные в ЛК ЗК на этапе заполнения сначала должны перейти в Галактику. Пока они не загружены не нужно сразу переходить в статус «Выверка». Если админ выбирает этот режим, то возникает попап «Переход в режим выверки, данные будут выгружены в Галактику при следующей синхронизации. Переход в режим выверки должен происходить только один раз в год. Вы уверены?». Да/Нет. Если согласился, то переходим в специальный режим «Выгрузка данных в Галактику», который нельзя выбрать в селекте режимов и этот селект режимов переходит в режим ридонли. В этом режиме во вкладке «Нагрузка» у всех ролей пишется только «Выгрузка данных в Галактику. Информация тут будет доступна завтра.»
Надо добавить какой-нибудь url, по которому внешняя система будет считывать текущий режим работы ЛК ЗК.
Когда внешний сервис увидит, что система перешла в режим «Выгрузка данных в Галактику», то он до ночной синхронизации ЛК ЗК по выгрузкам xml (по распределению и созданию нагрузки) передаст все в Галактику, таким образом там, к моменту синхронизации ЛК ЗК, данные должны будут соответствовать данным, заполненным в ЛК ЗК.
Тут есть нюанс.. По созданным в ЛК ЗК нагрузкам (ИК/КСРО, аспирантура) выгрузка идет в два этапа — сначала надо создать саму нагрузку в Галактике (одна xml), потом привязать к этой созданной нагрузке уже Lecturer (вторая xml). Но пока нагрузка не создана, не известен base uid, соответственно не получится сформировать строки с распределением Lecturer по этой нагрузке. Поэтому тут потребуется возможность после создания нагрузки в Галактике, чтобы ЛК ЗК считал данные снова, нашел по LoadId созданные нагрузки у которых нет еще base uid, и прописал его, чтобы внешняя система синхронизации увидела в xml с привязками эти новые uid и выгрузила в Галактику. То-есть нужен какой-то url в ЛК ЗК, при вызове которого он забирает все xml из Галактики и проставляет у себя base uid (там где его нет) по LoadId. То-есть порядок действий при переключении режимов получается такой:
1) Забирается из ЛК ЗК файл xml с новой, созданной там, нагрузкой, передается в Галактику
2) Из Галактики формируются данные по нагрузке (все xml, включая ContentOfLoad и т. п.)
3) Вызывается скрипт, чтобы ЛК ЗК забрал свежие данные и проставил base uid.
4) Забирается из ЛК ЗК файл xml с распределением по Lecturer, передается в Галактику
5) Снова из Галактики формируются данные по нагрузке чтобы там уже были эти новые привязки Lecturer.
6) Запускается основная ежедневная синхронизация ЛК ЗК, которая заново считывает все xml Галактики по нагрузке.
При ночной синхронизации если система видит, что режим стоит «Выгрузка в ГУВ», сначала автоматически меняет режим на «Выверка», очищает вообще все сплиты, вручную созданную нагрузку в ЛК ЗК (точнее куда-то все бэкапит, в другие таблицы, иначе если что-то пойдет не так, то вся работа по заполнению ЛК ЗК пропадет) и дальше начинает работать по логике этого режима.
В режиме «Выверка»:
Загружаются данные из Галактики, при этом при каждой синхронизации в этом режиме в начале очищаются все сплиты в ЛК ЗК (если появились).
Завкаф видит вообще всё (все строки, КСРО, аспирантуры) в режиме ридонли. Но возможность отправить запрос в УОУП у него из таблицы остаётся.
У УОУП появляется возможность менять привязки ППС (как до этого делал завкаф). Только эта возможность появляется, а всякие КСРО, аспирантура и прочее остаются в ридонли. Если что-то поправил, то это сохраняется в сплитах. За основу берется текущие привязки (если были) из Галактики по этой базе, то-есть например если из Галактики пришло что на одну базовую строку привязано 3 ППС, а он поправил одного, то в сплитах должна сохраниться новая привязка на всех трёх. То-есть если есть сплит, то в этом режиме приоритет показа в таблице на него, если нет, то из Галактики. Дальше по xml выгрузкам ежедневно отдельный скрипт (до основной синхронизации ЛК ЗК) передаст сплиты в Галактику, таким образом в этом режиме в начале синхронизации можно все сплиты чистить и брать уже актуальное текущее распределение из Галактики.
Фактически в этом режиме идет просмотр данных, которые прописаны в Галактике, с минимальной возможностью корректировки в части привязки ППС к нагрузке.

Архив
Все данные находятся в режиме ридонли для всех.
Данные по нагрузке каждый день импортируются в ЛК ЗК и показываются для просмотра.
